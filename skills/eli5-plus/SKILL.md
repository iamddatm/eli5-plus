# eli5-plus

面向零基础读者解释复杂主题，让读者不只知道“它是什么”，还理解“为什么需要它、怎么工作、什么时候有用”。

ELI5+ 的目标是建立正确的心智模型（mental model），不是模仿幼儿说话。使用大白话、短句和具体例子，同时保留会影响结论的机制、限制和取舍。

用户的明确要求优先于本 skill 的默认建议。用户指定语言、受众、文件位置、讲解范围或动效偏好时，按用户要求执行。

## 核心方法 Core approach

根据主题选择最有助于理解的内容。下面是可取舍的菜单，不是必须照抄的模板：

1. 用一句话说清核心概念。
2. 先解释它要解决什么问题，以及为什么会出现。
3. 使用具体场景、例子或类比。
4. 在有帮助时，用图表达结构、关系、流程或数据流。
5. 先讲真实机制，再引入专业术语（professional terms）。
6. 补充最重要的边界、取舍、常见误区或概念对比。
7. 用简短总结收尾，让读者记住核心关系。

保持因果链清晰：输入或条件 → 发生什么 → 输出或影响。优先讲清少量相互连接的概念，而不是罗列事实。通过层次和视觉压缩表达。

## 复杂模式 Complex mode

当主题包含三个或更多相互依赖的子机制，或完整因果链无法在不把关键机制压成一句话的前提下讲清时，启用复杂模式；其余主题仍按「核心方法」一节的粒度组织。

复杂模式按以下顺序执行：

1. 先拆分：列出子点及其依赖或先后关系，形成因果链或层次地图；首屏以这张总图作为核心结论，让读者第一时间看到每个点在整体中的位置。
2. 逐点深潜：每个子点获得独立小节，深度至少包含直觉解释、真实机制和一个具体例子或状态变化；用户点名要弄懂的机制不允许用“然后进行相关处理”这类空转措辞带过。子点过多时，把相邻子点合并进同一小节，深度下限按合并后的组逐组核对。
3. 周边不丢：与主链相邻、共同决定因果完整性的周边机制，不因页面篇幅被整段删除；确需简化时，在页面中明确标注“本版对哪些环节做了简化”。
4. 回汇收束：结尾沿总图把子点逐一收拢，重新呈现整体心智模型，让读者带走的是连通的链，不是散落的片段。

反向闸：逐点深潜不等于页面退回文字堆砌。每节内部仍执行“大图少字、一节一个重点”，示意数字声明、类比失效标注、来源区分等准确性与视觉规则在复杂模式下同样生效；增量必须来自机制密度，不能来自重复或铺垫。

## 准确性与讲解边界 Accuracy and teaching boundaries

- 明确标注“类比”（analogy），并说明类比在哪些地方不再成立。
- 先用大白话解释，再引入专业术语；引入后保持术语含义前后一致。
- 如果某个误区可能导致错误的心智模型，要主动纠正。
- 说明有意义的限制、失败模式、前提和取舍。
- 使用文档、代码或数据时，区分“来源明确写了什么”“由此推断什么”和“哪些内容尚未验证”。
- 对当前、冷门、高风险或依赖外部资料的事实，按需使用权威来源核实，并在页面中保留有价值的来源链接。

## 视觉表达 Visual language

选择能够最直接表达含义的视觉形式：

- 结构或层级（structure/hierarchy）→ 标注清晰的结构图；
- 关系或对比（relationship/comparison）→ 关系图、对比卡片或表格；
- 流程或数据流（process/data flow）→ 流程图；
- 随时间发生的交互（interaction over time）→ 时序图；
- 状态变化（state change）→ 状态图或有意义的动画。

视觉是解释的一部分，不是装饰。每个视觉元素应表达一个清晰重点，使用可读标签，并配有文字或可访问标记，使读者不看动画也能理解。追求大而清晰的视觉和“一节一个重点”；首屏优先呈现核心结论，主题确实需要更多深度时允许页面自然延展。

坚持“大图少字”：每节优先用一张主视觉承载核心关系，文字只保留标题、关键标签、必要解释和边界。

适当使用内联 HTML、CSS、SVG 和 JavaScript，使页面作为 standalone HTML 离线打开时不依赖外部运行资源；外部链接仅作引用。

只有当运动能帮助读者理解流程、状态转换或数据流时才使用动画。动画必须表现内容或状态真实变化，不能只是让完成后的结果闪烁、脉冲或高亮。提供可读的静态状态或 fallback，遵守 `prefers-reduced-motion: reduce`。

用于解释过程的非首屏动画，应在进入视区时自动播放一次，并保留暂停、重播或逐步查看能力；在减少动效模式下直接展示静态结果。

## HTML 交付 HTML delivery

始终在当前工作区或用户指定的位置创建完整、独立的 `.html` 文件，然后返回该文件的可点击链接。

页面应使用语义化 HTML，具备响应式布局、明确的视觉层级并易于扫描。至少包含文档标题、语言声明、viewport 元信息和清晰的内容层级。

## 红线 Red lines

以下任何一条都算交付失败：

- 凭空编造精确数字或确定性结论；
- 把概念描述成万能或神奇的黑盒；
- 用类比替代真实机制，或为“简短”删掉会改变含义的关键限定；
- 声称存在没有实现或没有验证过的动画、图片或交互；
- 页面渲染或核心解释依赖远程图片、字体、库或服务；
- 把长篇正文拆成文字卡片伪装成视觉化，或为满足清单添加没有解释价值的视觉、动画或交互；
- 强迫所有主题使用同一种布局；
- 把聊天中粘贴原始 HTML 当作主要交付物。

## 异常与降级 Failures and fallbacks

| 触发条件 | 一线修复 | 仍失败时的兜底 |
|---|---|---|
| 启用复杂模式并允许延展后仍装不下，或受众口径会明显改变选材取舍 | 🔴 先问 1-2 个收窄问题（范围、受众、期望深度）再动工 | 用户表示“都行”或不回应：选最合理的默认范围，并在页首写明该口径 |
| 事实依赖时效、冷门或不可得来源，无法核实 | 只讲稳定成立的原理，把该论点标为“存疑”并说明缺什么 | 该点决定核心结论时，直接告知用户缺少哪部分依据，不猜测补齐 |
| 素材引用了远程图片或其他外部资源 | 本地内联替换，或重绘等价的 SVG | 重绘会失真时保留文字解释，标注该视觉离线不可用 |
| 动画实现不了，或页面反复增改后持续膨胀 | 降级为静态图加分步文字，删除纯装饰动画 | 静态也无法表达过程时改用流程图，并守住“视觉表达”节的动画诚实规则 |
| 复杂模式子点多到逐组满足深度下限会失控 | 按复杂模式第 2 步的合并办法处理 | 合并仍失控时，确需简化的周边环节按复杂模式第 3 步标注，保住主链深度 |
| 无法在浏览器中渲染页面 | 按完成前检查完成静态解析与脚本语法检查，如实报告验证范围；连解析器都没有时人工核对标签配平 | 不表述为视觉质量已验证，提示用户本地抽查窄屏和宽屏 |

## 完成前检查 Final checks

🔴 报告完成前，逐项检查实际生成的文件；任一项未通过都不得报告完成：

- 文件存在、非空，并能作为独立文档打开；
- 解释回答了主题相关的“是什么、为什么、怎么工作、何时有用”；
- 类比、真实机制、限制和来源没有互相混淆或产生误导，且不触犯「红线」任何一条；
- 视觉元素相关、清晰、对齐，并提供静态或可访问路径；
- 检查每节是否有明确的视觉中心；能够由图形、关系、流程或状态表达的内容，不应主要依靠连续大段文字说明；
- 启用复杂模式时：首屏给出总图、每个子点（或合并后的组）达到深度下限、被简化的环节已在页面中标注；
- 所有声称存在的动画或交互都已实现且能工作；
- 页面不依赖外部运行资源；
- 至少使用可用的解析器完成 HTML 静态解析；包含 JavaScript 时，再执行脚本语法检查；
- 具备浏览器能力时，分别在窄屏和宽屏渲染，检查内容溢出、遮挡、错位、文字可读性以及动画和交互。
